# P5.3 — P5 Closure & Verification

## Objetivo

A P5.3 é uma fase de fechamento e verificação da P5.

Ela não introduz novas capacidades de produto.

Seu objetivo é:

1. auditar a implementação atual contra as specs P5.1 e P5.2;
2. identificar qualquer item ainda pendente ou divergente;
3. implementar/corrigir os gaps encontrados;
4. validar integração entre P5.1 e P5.2;
5. garantir testes, OpenAPI, migrations, documentação e versionamento consistentes;
6. deixar a P5 completamente concluída antes do início da P6.

A implementação deve trabalhar sobre o estado REAL do repositório, não assumir que os status dos planos anteriores representam necessariamente o estado atual do código.

---

# 1. Escopo

A P5.3 cobre exclusivamente:

```text
P5.1 — Support / Ops Foundation
        +
P5.2 — Priority Policy + Ops Queue
        +
P5 closure / regression / documentation
```

Fora de escopo:

- novas features de P6;
- recálculo automático de prioridade;
- notificações;
- SLA;
- leitura de Messages por Ops;
- frontend;
- IA/LLM;
- novos canais de comunicação;
- mudanças de arquitetura não exigidas pelos gaps encontrados.

1. inspecionar o repositório atual;

# 5. P5.1 — Internal Comments

Confirmar:

```text

GET  /v1/ops/order-items/{item_id}/internal-comments
```

e:

```text
POST /v1/order-items/{item_id}/internal-comments
GET  /v1/order-items/{item_id}/internal-comments
```

Os dois paths devem utilizar a mesma tabela:

```text
internal_comments
```

## Regras

Validar:

- Ops pode criar/consultar;
- Seller pode criar/consultar somente no próprio item;
- Buyer não possui acesso;
- Seller de outra loja recebe `404`;
- comentário pertence diretamente ao Order Item;
- não depende de Conversation;
- comentários são imutáveis;
- `PATCH` e `DELETE` retornam `405`;
- conteúdo entre 1 e 2000 caracteres;
- conteúdo vazio/branco retorna `422`;
- identidade do autor vem do JWT;
- `author_type` enviado pelo cliente não pode substituir o papel real.

Body esperado:

```json
{
  "content": "..."
}
```

Campos extras devem seguir o comportamento Pydantic existente no projeto e não devem ser transformados artificialmente em `422`.

# 10. P5.2 — Priority Formula

Validar os pesos definidos pela spec.

## Reason

```text
atraso       = 1.00
reclamacao   = 0.75
troca        = 0.50
devolucao    = 0.50
suporte      = 0.40
outros       = 0.25
elogio       = 0.00
```

## Order Item Status

```text
in_transit   = 1.00
preparing    = 0.75
placed       = 0.50
delivered    = 0.25
cancelled    = 0.00
```

## Conversation Age

```text
< 4h          = 0.00
4h–12h        = 0.25
12h–24h       = 0.50
24h–48h       = 0.75
>= 48h        = 1.00
```

## Purchase Price

```text
< 100         = 0.00
100–499       = 0.25
500–999       = 0.50
1000–4999     = 0.75
>= 5000       = 1.00
```

Valor utilizado é o:

```text
OrderItem.purchase_price
```

e não:

```text
Product.price
```

Não multiplicar por quantidade na V1.

# 13. P5.2 — Ops Queue

Confirmar:

```http
GET /v1/ops/conversations
```

A fila deve conter somente:

```text
Conversation.status = OPEN
```

CLOSED não aparece na fila.

## Ordenação

A ordenação deve ocorrer no SQL:

```text
CRITICAL
HIGH
MEDIUM
LOW
```

e dentro da mesma prioridade:

```text
last_interaction_at DESC
```

Não ordenar a página em Python depois de buscar os registros.

## Effective priority

No SQL:

```sql
CASE
    WHEN ops_override = 'critical'
        THEN 'critical'
    ELSE calculated_priority
END
```

# 17. P5.2 — Priority Refresh

Confirmar:

```http
POST /v1/ops/conversations/{id}/priority/refresh
```

O refresh deve:

1. obter o estado atual;
2. recalcular `calculated_priority`;
3. persistir;
4. manter `ops_override` intacto.

Se houver:

```text
ops_override = critical
```

o refresh não deve apagar nem substituir o override.

Não implementar refresh automático.

---

# 18. P5.2 — Critical Override

Confirmar:

```http
POST /v1/ops/conversations/{id}/critical
```

Com:

```text
ops_override = critical
```

Regras:

- somente Ops;
- Conversation deve existir;
- operação deve ser segura sob concorrência;
- utilizar `SELECT FOR UPDATE` conforme spec;
- `calculated_priority` permanece inalterada;
- prioridade efetiva passa a ser `critical`;
- justificativa deve ser registrada como `InternalComment`.

Se já estiver `critical`:

```text
409
```

---

# 19. P5.2 — Remove Critical

Confirmar:

```http
POST /v1/ops/conversations/{id}/critical/remove
```

Regras:

- somente Ops;
- `ops_override` volta para `NULL`;
- `calculated_priority` permanece intacta;
- prioridade efetiva volta para a calculada.

Se não existir override:

```text
409
```

A remoção não deve apagar o histórico do `InternalComment`.
