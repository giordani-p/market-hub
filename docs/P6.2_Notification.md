# P6.2 — Notifications + Notification Delivery Foundation

## 1. Objetivo

Implementar a P6.2 do Market Hub, adicionando notificações internas (in-app) para mudanças de estado de negócio e preparando uma fundação simples para futuros canais como Email, Slack e WhatsApp.

A implementação deve reutilizar a infraestrutura assíncrona criada na P6.1:

```text
Domain Event
    ↓
Notification Job
    ↓
SQS
    ↓
Worker
    ↓
Notification Service
    ↓
In-App Notification
```

Separar claramente:
- o evento de negócio;
- a Notification criada para um destinatário;
- o canal utilizado para entrega.

Nesta fase, somente `IN_APP` será implementado.

---

## 2. Escopo funcional

Toda mudança válida de status em:
- `OrderItem`;
- `Conversation`;

deve gerar uma Notification.

`MessageCreated` não é gatilho nesta fase.

### Destinatários

- `OrderItem` status changed → Buyer + Seller.
- `Conversation` status changed → Buyer + Seller.
- Ops não recebe automaticamente essas notificações genéricas.

---

## 3. Arquitetura

```text
OrderItem / Conversation
        │
        │ status change
        ▼
   Domain Event
        │
        ▼
 Notification Job
        │
        ▼
       SQS
        │
        ▼
      Worker
        │
        ▼
 Notification Service
        │
        ├──► InAppChannel
        │        ↓
        │    PostgreSQL
        │
        └──► Delivery Layer
                 ├── Email (future)
                 ├── Slack (future)
                 └── WhatsApp (future)
```

Reutilizar Job/SQS/Worker da P6.1. Não criar outra infraestrutura de filas ou Workers.

---

## 4. Domain Events

Reutilizar os Domain Events existentes.

Eventos notificáveis:
- `OrderItemStatusChanged`;
- eventos existentes que representem mudança de status de `Conversation`.

Não usar `MessageCreated` como gatilho.

Não duplicar a detecção de mudança de estado no Notification Service. O domínio continua responsável por emitir o evento.

---

## 5. Notification Job

Criar um Job:

`NOTIFY_STATUS_CHANGE`

O Job representa o contexto da mudança, não uma Notification individual.

Exemplo:

```json
{
  "type": "NOTIFY_STATUS_CHANGE",
  "entity_type": "ORDER_ITEM",
  "entity_id": 123,
  "previous_status": "PROCESSING",
  "new_status": "SHIPPED"
}
```

Para Conversation:

```json
{
  "type": "NOTIFY_STATUS_CHANGE",
  "entity_type": "CONVERSATION",
  "entity_id": 456,
  "previous_status": "OPEN",
  "new_status": "CLOSED"
}
```

Não colocar o estado completo da entidade no Job. O Worker/Service deve consultar o estado atual do banco.

---

## 6. Domain Event → Job

Quando um Domain Event notificável ocorrer:

```text
Domain Event
    ↓
NOTIFY_STATUS_CHANGE
    ↓
SQS
```

O envio deve ser assíncrono.

Não executar a criação da Notification diretamente no fluxo síncrono da API.

### Garantia

Aceitar a possibilidade de falha entre:

```text
DB commit → SQS publish
```

Não implementar Outbox nesta fase. Essa decisão poderá ser revisitada posteriormente.

---

## 7. Notification Service

Criar um serviço de aplicação responsável por transformar o Job em Notifications.

Responsabilidades:
1. interpretar o Job;
2. identificar a entidade;
3. carregar o contexto;
4. determinar destinatários;
5. construir a Notification;
6. encaminhar para o canal;
7. garantir idempotência.

Não duplicar regras de negócio existentes no domínio.

---

## 8. Modelo Notification

Criar entidade persistida:

```text
Notification
├── id
├── recipient_id
├── type
├── title
├── message
├── entity_type
├── entity_id
├── metadata
├── created_at
└── read_at
```

### Semântica

- `recipient_id`: usuário destinatário.
- `type`: tipo semântico, inicialmente `ORDER_ITEM_STATUS_CHANGED` e `CONVERSATION_STATUS_CHANGED`.
- `title`: texto pronto para apresentação.
- `message`: texto pronto para apresentação.
- `entity_type`: `ORDER_ITEM` ou `CONVERSATION`.
- `entity_id`: recurso originador.
- `metadata`: dados estruturados da transição.
- `created_at`: criação.
- `read_at`: `NULL` = unread; timestamp = read.

Exemplo de metadata:

```json
{
  "previous_status": "PROCESSING",
  "new_status": "SHIPPED"
}
```

O backend deve gerar `title` e `message`; o frontend não deve reconstruir regras de negócio.

---

## 9. Idempotência

Uma mesma mudança de estado não pode criar múltiplas Notifications para o mesmo destinatário em caso de retry, duplicação ou reprocessamento.

Usar constraint única no banco baseada no contexto lógico:

```text
recipient_id
notification_type
entity_type
entity_id
previous_status
new_status
```

Exemplo:

```text
OrderItem #123
PROCESSING → SHIPPED
Buyer
```

deve produzir somente uma Notification para aquele Buyer. O Seller terá sua própria Notification.

Não criar `processed_events`, event store ou mecanismo externo de idempotência.

---

## 10. Notification Channel

Criar uma abstração mínima:

```text
NotificationChannel
    └── send(notification, recipient)
```

Implementar somente:

```text
InAppNotificationChannel
```

O canal in-app persiste a Notification no PostgreSQL.

Deixar a arquitetura preparada para:

```text
NotificationChannel
├── InAppNotificationChannel
├── EmailNotificationChannel
├── SlackNotificationChannel
└── WhatsAppNotificationChannel
```

Não implementar os canais externos agora.

---

## 11. Delivery Layer

Separar:

> Notification = o que aconteceu e quem precisa ser informado.

> Channel = como a informação será entregue.

Futuramente:

```text
Notification
    ↓
Delivery Orchestrator
    ├── IN_APP
    ├── EMAIL
    ├── SLACK
    └── WHATSAPP
```

Não criar integrações externas ou mocks desnecessários nesta fase.

---

## 12. APIs

Implementar:

```text
GET  /v1/notifications
GET  /v1/notifications/unread-count
PATCH /v1/notifications/{notification_id}/read
PATCH /v1/notifications/read-all
```

### Listagem

- retornar somente Notifications do usuário autenticado;
- suportar paginação;
- ordenar por `created_at DESC`.

### Unread count

Retornar apenas a contagem do usuário autenticado.

### Mark as read

Operação idempotente. Não permitir acessar/alterar Notification de outro usuário.

### Mark all as read

Marcar todas as Notifications não lidas do usuário como lidas. Operação idempotente.

---

## 13. Autorização

Reutilizar Authentication/Authorization existentes.

Usuário somente pode:
- consultar suas Notifications;
- consultar sua contagem;
- marcar suas Notifications como lidas.

Não criar mecanismo paralelo.

---

## 14. Persistência

Criar migration Alembic para `Notification`.

Garantir:
- banco existente;
- banco criado do zero;
- padrões atuais do projeto;
- índices adequados;
- constraint de idempotência.

Considerar índices por:
- `recipient_id`;
- `read_at`;
- `created_at`.

Não alterar migrations já aplicadas.

---

## 15. Falhas no Worker

Reutilizar P6.1:

```text
SQS receive
    ↓
Notification Job
    ↓
Notification Service
    ↓
success
    ↓
delete message
```

Em falha:

```text
SQS receive
    ↓
failure
    ↓
message NOT deleted
    ↓
retry
    ↓
DLQ
```

Não implementar retry paralelo nem lifecycle persistido de Job.

---

## 16. Eventual Consistency

Notifications são assíncronas.

É aceitável existir pequena janela entre a mudança de status e a disponibilidade da Notification.

Não bloquear a operação principal esperando a Notification.

---

- Conversation status changed;
- `MessageCreated` não gera Notification;
- Buyer e Seller recebem Notification;

- metadata;

### Idempotência

- unread count;
- mark as read;
- mark all as read;

- não delete após falha;
