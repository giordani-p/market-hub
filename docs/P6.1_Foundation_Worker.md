# P6.1 — Background Processing Foundation + Automatic Priority Recalculation

## 1. Objetivo

Implementar a P6.1 do Market Hub, introduzindo uma fundação de processamento assíncrono preparada para evolução futura para AWS e utilizando essa fundação para realizar a reconciliação automática de prioridades de Conversations.

A implementação deve manter a arquitetura atual do projeto, evitando introduzir componentes ou padrões que não sejam necessários neste momento.

### Resultado esperado

A cada 15 minutos:

1. O Scheduler dispara o Job `RECONCILE_PRIORITIES`.
2. O Job é publicado em uma fila SQS local.
3. O Worker consome o Job.
4. O Worker executa o handler/application service correspondente.
5. O processamento busca Conversations `OPEN` potencialmente stale.
6. O processamento ocorre em páginas.
7. A prioridade é recalculada usando a Priority Policy V1 existente.
8. O banco é atualizado somente quando houver mudança efetiva.
9. O processamento é idempotente.
10. Falhas seguem o fluxo de retry do SQS e, após as tentativas configuradas, chegam à DLQ.

A implementação local deve usar Docker + LocalStack, com abstrações/adapters que permitam uma futura substituição por serviços AWS reais.

---

## 2. Contexto e restrições arquiteturais

### Stack

- Backend: Python + FastAPI
- Banco: PostgreSQL
- ORM: SQLAlchemy
- Migrations: Alembic
- Ambiente local: Docker Compose
- AWS local: LocalStack
- Mensageria: SQS
- Scheduling: EventBridge Scheduler via LocalStack

### Arquitetura atual

O projeto possui uma única aplicação FastAPI organizada por domínio, e não por camadas técnicas genéricas.

Manter essa organização.

Não introduzir nesta fase:

- microservices;
- Kafka;
- Redis;
- Kubernetes;
- Event Sourcing;
- CQRS;
- Outbox Pattern;
- distributed locks;
- Event Bus;
- banco separado para Jobs;
- persistência de lifecycle/status de Jobs.

O objetivo é criar uma fundação simples, explícita e evolutiva.

# 3. Conceitos principais

## 3.1 Job

Criar uma abstração genérica de Job.

O Job representa uma unidade de trabalho assíncrona, mas não deve conter regra de negócio.

O primeiro Job será:

`RECONCILE_PRIORITIES`

A abstração deve permitir que novos Jobs sejam adicionados posteriormente, especialmente para a P6.2 — Notifications.

O payload deve ser pequeno e conter apenas informações necessárias para identificar o tipo de Job e seus parâmetros.

Não colocar no payload o estado das Conversations.

O Worker deve consultar o estado atual do banco no momento da execução.

---

## 3.2 Job Handler

Cada tipo de Job deve possuir um handler responsável por delegar sua execução para a lógica de aplicação correspondente.

O Worker não deve conhecer regras de negócio.

Fluxo esperado:

```text
SQS message
    ↓
Worker
    ↓
Job dispatcher / registry
    ↓
Job Handler
    ↓
Application Service / Domain
```

O Worker deve cuidar somente de:

- consumir mensagens;
- interpretar o Job;
- localizar o handler;
- executar o handler;
- reconhecer/deletar a mensagem em caso de sucesso;
- deixar a mensagem disponível para retry em caso de falha.

---

# 4. Background Processing Foundation

## 4.1 Scheduler

Utilizar LocalStack para simular a integração com:

`EventBridge Scheduler → SQS`

O Scheduler deve executar a cada:

**15 minutos**

O Scheduler não deve possuir lógica de negócio.

Sua única responsabilidade é disparar o Job:

`RECONCILE_PRIORITIES`

### Importante

Não implementar um scheduler Python customizado.

A solução deve utilizar o mecanismo de scheduling do LocalStack/EventBridge para manter uma aproximação mais próxima da futura arquitetura AWS.

Não é necessário reproduzir todos os recursos do EventBridge Scheduler. Apenas o comportamento necessário para disparar o Job periodicamente.

---

## 4.2 SQS

Criar uma fila local para processamento dos Jobs.

Sugestão de nome:

`market-hub-jobs`

O nome final pode seguir a convenção já existente no projeto, caso exista.

Configurar a fila considerando processamento:

**at-least-once**

A solução não deve assumir exatamente-once delivery.

O processamento dos Jobs deve, portanto, ser idempotente.

---

## 4.3 DLQ

Criar uma Dead Letter Queue local.

Sugestão:

`market-hub-jobs-dlq`

Configurar a fila principal para encaminhar mensagens para a DLQ após o número de tentativas definido pela implementação.

O valor exato de `maxReceiveCount` pode ser definido pela implementação de infraestrutura, desde que:

- esteja documentado;
- seja configurável;
- permita demonstrar o fluxo de retry → DLQ em testes/verificação.

---

## 4.4 Worker

Criar um processo/container separado para o Worker.

O Worker deve:

1. conectar ao SQS;
2. fazer polling da fila;
3. receber uma mensagem;
4. interpretar o Job;
5. localizar seu handler;
6. executar o handler;
7. deletar a mensagem somente após sucesso.

### Concorrência

O Worker deve processar:

**1 Job por vez.**

Não implementar concorrência paralela nesta fase.

A arquitetura, entretanto, deve evitar impedir uma evolução futura para múltiplos Workers/concorrência.

---

# 5. Tratamento de falhas

O processamento deve seguir o comportamento natural do SQS.

### Sucesso

```text
receive
  ↓
execute
  ↓
success
  ↓
delete message
```

### Falha

```text
receive
  ↓
execute
  ↓
exception
  ↓
message NÃO é deletada
  ↓
SQS retry
  ↓
...
  ↓
DLQ
```

O Worker não deve implementar manualmente um mecanismo paralelo de retry.

Não persistir status de Job no PostgreSQL.

---

# 6. Priority Reconciliation

## 6.1 Job

Implementar:

`RECONCILE_PRIORITIES`

Este será um Job de **batch**.

Não criar um Job individual para cada Conversation.

O Job deve localizar Conversations que precisam de reconciliação e processá-las em páginas.

---

## 6.2 Escopo do processamento

O Job deve buscar somente:

- Conversations `OPEN`;
- Conversations potencialmente stale.

Não recalcular indiscriminadamente todas as Conversations.

Conversations `CLOSED` não devem ser processadas pela reconciliação automática.

---

# 7. Stale Detection

Adicionar/persistir as informações necessárias para identificar quando o snapshot da prioridade precisa ser recalculado.

## 7.1 Conversation

Adicionar:

`priority_calculated_at`

Semântica:

> Momento em que `calculated_priority` foi calculada com base no estado atual conhecido.

Esse campo deve ser atualizado sempre que a prioridade for recalculada.

---

## 7.2 OrderItem

Adicionar:

`status_updated_at`

Semântica:

> Momento da última alteração do status do OrderItem.

Esse campo deve ser atualizado quando o status do OrderItem mudar.

---

## 7.3 Condição de stale

Uma Conversation `OPEN` é considerada stale quando qualquer uma das condições abaixo for verdadeira:

```text
last_interaction_at > priority_calculated_at
```

OU

```text
status_updated_at > priority_calculated_at
```

OU

```text
age_bucket(now) != age_bucket(priority_calculated_at)
```

A implementação deve tratar corretamente valores nulos, especialmente quando `priority_calculated_at` ainda não existir.

Uma Conversation que ainda não possui cálculo válido de prioridade deve ser considerada candidata à reconciliação.

---

# 8. Age Buckets

A reconciliação deve respeitar os mesmos buckets temporais utilizados pela Priority Policy V1.

Buckets:

```text
< 4h
4h – 12h
12h – 24h
24h – 48h
> 48h
```

A mudança de bucket é suficiente para tornar o snapshot stale, mesmo que nenhuma nova mensagem ou alteração de status tenha ocorrido.

Isso garante que a prioridade baseada em idade evolua automaticamente.

---

# 9. Recalculation

A Priority Policy V1 existente deve continuar sendo a fonte de verdade para o cálculo.

Não duplicar a regra de prioridade dentro do Scheduler ou Worker.

O fluxo deve ser:

```text
RECONCILE_PRIORITIES
    ↓
find stale OPEN Conversations
    ↓
load current state
    ↓
calculate priority using existing policy
    ↓
compare with persisted calculated_priority
    ↓
update only if necessary
```

A prioridade efetiva deve continuar respeitando o `ops_override` existente.

### Importante

O `ops_override` não deve ser alterado ou removido pela reconciliação.

A reconciliação atualiza apenas a prioridade calculada.

A prioridade efetiva continua sendo derivada de:

```text
calculated_priority
+
ops_override
```

conforme as regras existentes.

---

# 10. Idempotência

O Job deve ser idempotente.

Uma execução repetida sobre o mesmo estado não deve produzir efeitos adicionais.

Se a prioridade recalculada for igual à prioridade já persistida:

- não realizar UPDATE desnecessário;
- não gerar efeitos colaterais;
- não produzir notificações nesta fase.

Isso também protege contra:

- retry do SQS;
- duplicação de mensagem;
- sobreposição de execuções;
- eventual execução repetida do Scheduler.

---

# 11. Paginação

O processamento do batch deve utilizar paginação.

Não carregar todas as Conversations stale em memória de uma única vez.

O tamanho da página deve ser configurável ou seguir uma constante claramente documentada.

A implementação deve permitir processar:

```text
page 1
  ↓
page 2
  ↓
page 3
  ↓
...
```

até não existirem mais candidatos.

A paginação deve ser implementada de forma consistente com o ORM/DB utilizado pelo projeto.

---

# 12. Execuções sobrepostas

O Scheduler continuará disparando a cada 15 minutos mesmo que uma execução anterior ainda esteja em processamento.

Não implementar distributed lock nesta fase.

A segurança deve vir de:

- processamento idempotente;
- leitura do estado atual;
- seleção de Conversations stale;
- atualização somente quando houver mudança.

Se uma segunda execução encontrar uma Conversation que já foi reconciliada pela primeira, ela deverá simplesmente não produzir alteração adicional.

---

# 13. Abstração de infraestrutura

Criar interfaces/ports suficientes para separar a lógica de aplicação da infraestrutura específica do LocalStack.

Exemplo conceitual:

```text
Application
    ↓
Job abstraction / Queue port
    ↓
SQS adapter
    ↓
LocalStack
```

O objetivo é permitir futuramente:

```text
LocalStack SQS
      ↓
AWS SQS
```

sem alterar a lógica de negócio.

Da mesma forma, a configuração do Scheduler deve ficar isolada da aplicação.

Não criar uma abstração excessivamente genérica ou um framework interno de mensageria.

A abstração deve ser mínima e suficiente para a necessidade atual.

# 19. Testes

A implementação deve incluir testes suficientes para demonstrar o comportamento da nova infraestrutura e da reconciliação.

## 19.1 Unit tests

Cobrir pelo menos:

- stale quando `last_interaction_at` é posterior ao cálculo;
- stale quando `status_updated_at` é posterior ao cálculo;
- stale quando o age bucket mudou;
- não stale quando nenhum critério mudou;
- Conversation sem `priority_calculated_at`;
- recalculation usando a Priority Policy existente;
- preservação de `ops_override`;
- nenhuma atualização quando a prioridade não mudou;
- processamento idempotente.

---

## 19.2 Application/integration tests

Cobrir:

- `RECONCILE_PRIORITIES` processando múltiplas Conversations;
- processamento paginado;
- somente Conversations `OPEN`;
- Conversations `CLOSED` ignoradas;
- atualização de `priority_calculated_at`;
- alteração de prioridade persistida corretamente;
- execução repetida sem efeitos adicionais.

---

## 19.3 Worker tests

Cobrir:

- Worker identifica o Job corretamente;
- handler correto é chamado;
- mensagem é deletada após sucesso;
- mensagem não é deletada quando o handler falha;
- erro é propagado para permitir retry do SQS.

---

## 19.4 Infrastructure / E2E verification

Sempre que viável, validar o fluxo:

```text
EventBridge Scheduler
        ↓
       SQS
        ↓
      Worker
        ↓
RECONCILE_PRIORITIES
        ↓
```

```text
    ↓
```

# 25. Definition of Done

A P6.1 deve terminar com uma fundação de background processing funcional, simples e evolutiva, na qual:

```text
EventBridge Scheduler
        │
        │ every 15 minutes
        ▼
      SQS
        │
        ▼
      Worker
        │
        ▼
Job Handler
        │
        ▼
Priority Reconciliation
        │
        ▼
   Priority Policy
        │
        ▼
   PostgreSQL
```

O resultado deve permitir que a próxima fase, especialmente **P6.2 — Notifications**, reutilize a mesma infraestrutura de Scheduler/SQS/Worker/Job sem precisar redesenhar a fundação de processamento assíncrono.
